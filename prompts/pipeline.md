description: 多 Agent 并行流水线：拆任务 → worktree 并行实施 → 审查 → 合并，每个阶段结束停下等确认。
---

针对以下目标推进多 Agent 流水线：$@

你（主 Agent）是调度者。流水线状态只存在目标仓库根目录的 `TASKS.md` 里；每次调用先读它，判断处于哪个阶段，**只推进一个阶段就停下**，不得连跑多个阶段。

## 通用纪律

- `TASKS.md` 是唯一的任务状态源。todo 只可用来展示本次调用内的步骤进度，不得用 todo 记录或推断任务状态。
- 只有你编辑 `TASKS.md`，且只在主工作区编辑；worker、reviewer 不得碰它。
- 不信子 Agent 的自述：是否提交、测试是否通过，一律自己用 git 和测试命令核实。
- 任何阶段都禁止 `git push`、禁止 stash、禁止改动基线分支上的未提交内容。
- commit message 按 AGENTS.md 约定。
- 本次调用中任何一步出现计划外情况（worktree 已存在、分支名冲突、测试命令跑不起来），停下说明，不要自行修补。

## TASKS.md 格式

```markdown
# 流水线任务
- 目标：……
- 基线分支：main
- 测试命令：npm test

## T01 标题
- 状态：todo            # todo | passed | failed | done | 需人工
- 依赖：无              # 或 T02, T03
- 改动文件：src/a.ts, src/b.ts
- 验收标准：……
- 失败次数：0
- 反馈：                # 审查意见 / 测试失败摘要 / 合并冲突原因
```

`测试命令` 缺失或不确定时问用户，不要猜。

## 阶段判定

1. 没有 `TASKS.md` → 阶段 0。
2. 有状态为 `passed` 的任务，且用户在本条消息中明确要求合并 → 阶段 2。
3. 有 `passed` 任务但用户没要求合并 → 列出这些任务，问用户是否合并，停下。
4. 有依赖已满足的 `todo` 任务 → 阶段 1。
5. 以上都不满足 → 汇报剩余任务状态（含 `需人工` 的原因），停下。

## 阶段 0：拆任务

1. 前置检查：当前目录是 git 仓库，`git status --porcelain` 为空。
   - 不是 git 仓库：停下告诉用户「没有 git 就没有 worktree 隔离，每批只能跑 1 个任务」，让用户二选一：授权你执行 `git init` 并做首次提交，或接受每批 1 个任务、worker 直接在主工作区实施。不要自行选择。
   - 是 git 仓库但工作区不干净：停下说明。
2. 用 subagent 工具的 `chain`：`scout` 收集上下文 → `planner` 基于 `{previous}` 输出任务清单。要求 planner 按「先定契约，再并行」拆分：
   - 每个任务小到一次实施加测试即可验证；写清依赖、**预计改动文件的完整清单**、验收标准。
   - 第一个任务是骨架任务：建好目录、模块边界、共享状态的数据结构和各模块的接口签名（可以是空实现加测试桩）。
   - 之后的功能任务各自拥有独立文件，只通过骨架定义的接口交互，不改共享的中心文件。依赖只写真实的数据依赖，不要按开发先后顺序串依赖。
   - 接入共享文件（主场景、入口组件、路由等）的工作集中到最后的装配任务。
   - 输出中标明哪些任务可以同批并行；确实无法并行时说明原因。
3. 按上面的格式写入 `TASKS.md`（所有任务 `todo`），但**不要提交**。
4. 输出任务表后停下，等用户确认或修改。

## 阶段 1：并行实施 + 审查

1. 前置检查：主工作区除 `TASKS.md` 外没有未提交改动，当前在基线分支。
2. 选批次：从依赖全部 `done` 的 `todo` 任务里按编号顺序挑，最多 4 个，**改动文件清单两两不相交**；有交集的留到下一批。
3. 为每个任务建隔离目录：
   `git worktree add ../<仓库目录名>-wt/<ID> -b pipe/<ID> <基线分支>`
   分支已存在（上次失败留下的）时先 `git branch -D pipe/<ID>` 再建。
4. 用 subagent 工具的 `parallel`，每项 `agent: "worker"`，`cwd` 设为该任务 worktree 的绝对路径。task 必须包含：
   - 任务原文、验收标准、改动文件清单（只许改这些文件）、测试命令；
   - 上次的反馈（若有），说明这是返工；
   - 这句授权：「本任务授权你：worktree 缺少依赖时按锁文件安装（如 `npm ci`），不得新增或升级依赖；完成并通过测试后，在当前分支执行 `git add` 和 `git commit`。禁止 push、禁止切换或新建分支、禁止修改清单外文件。」
5. 自己核实每个 worktree：`git -C <wt> log --oneline <基线分支>..HEAD` 非空，且 `git -C <wt> status --porcelain` 为空。不满足的直接判 `failed`，不送审查。
6. 用 subagent 工具的 `parallel`，每项 `agent: "reviewer"`，`cwd` 同上。task 必须说明：改动已提交，用 `git diff <基线分支>...HEAD` 取改动（`git diff` 会是空的）；对照任务的验收标准和文件清单审查；运行测试命令并贴结果。
7. 回到主工作区更新 `TASKS.md`：审查结论为通过且测试通过 → `passed`；否则 → `failed`，失败次数 +1，反馈写审查问题和测试失败摘要（不超过 10 行）。
8. 输出结果表（ID、状态、一句话原因、worktree 路径）和本轮 subagent 用量后停下，等用户决定是否合并。

## 阶段 2：合并

1. 前置检查：主工作区除 `TASKS.md` 外没有未提交改动，当前在基线分支。
2. 对每个 `passed` 任务按编号顺序：
   1. `git merge --no-ff --no-commit pipe/<ID>`。
   2. 有冲突 → `git merge --abort`，标 `failed`，失败次数 +1，反馈写冲突文件。
   3. 无冲突 → 跑测试命令。失败 → `git merge --abort`，标 `failed`，失败次数 +1，反馈写测试失败摘要；通过 → `git commit`，标 `done`。
   注意：`TASKS.md` 自身不要混进合并提交，提交前确认暂存区里没有它。
3. 清理：`done` 的任务执行 `git worktree remove <wt>` 和 `git branch -d pipe/<ID>`；`failed` 的只 `git worktree remove <wt>`，分支保留供查看。worktree 有未提交改动导致 remove 失败时，不要加 `--force`，保留目录并在汇报里列出路径。
   阶段 1 第 5 步判 `failed` 的任务也在这一步一并清理。
4. `failed` 任务：失败次数 < 2 → 状态改回 `todo` 等下一轮返工；≥ 2 → 标 `需人工`，不再自动重试。
5. 汇报：合并了哪些、失败了哪些及原因、剩余 `todo` / `需人工` 数量，然后停下。用户再次 `/pipeline` 才进入下一轮。

此模板只定义协作流程，不绕过 Pi 的项目信任、权限网关或操作系统授权。
